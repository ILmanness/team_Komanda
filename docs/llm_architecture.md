# LLMProvider: контракт и реализации

`backend/app/ai.py` задаёт общий интерфейс `LLMProvider`. Игровой код не должен
зависеть от имени модели или формата ключа конкретного облака.

## Вызовы

- `generate(messages) -> str` возвращает непустой текст.
- `generate_structured(messages, response_model) -> response_model` запрашивает
  JSON по схеме Pydantic-модели и валидирует ответ локально. Неверный JSON или
  несоответствие схеме приводит к `LLMResponseError`; вызывающий код не должен
  применять такой результат к состоянию игры.
- `stream(messages)` выдаёт текстовые фрагменты по мере получения ответа.
  Оборванный поток, пустой ответ и повреждённый фрагмент дают
  `LLMResponseError`; уже полученные фрагменты не следует считать полным
  ответом до успешного завершения потока.

`messages` — последовательность словарей `{"role": "system|user|assistant",
"content": "..."}`. Для структурированного вызова передавайте класс `BaseModel`;
модели со строгими полями (`ConfigDict(extra='forbid')`) дают более предсказуемую
JSON Schema. Возможности JSON Schema самого внешнего API зависят от провайдера.

## Реализации и совместимость игры

- `MockLLMProvider` возвращает фиксированный текст. Для структурированного
  ответа тест может передать `structured_response`; результат всё равно
  проходит проверку Pydantic. Без заданного ответа метод сообщает
  `LLMResponseError`, а не выдумывает игровые данные. Потоковый вызов выдаёт
  тот же фиксированный текст одним фрагментом.
- `CompatibleLLMProvider` вызывает `/chat/completions` по адресу из настроек.
  Структурированный вызов посылает `response_format=json_schema` и затем
  проверяет `message.content` через Pydantic. Реализация не содержит имени
  модели Cloud.ru: URL и модель задаются в `.env`. Потоковый вызов использует
  `stream: true` и читает SSE-фрагменты до `[DONE]`.
- `get_provider()` выбирает реализацию по `AI_PROVIDER`. GameService и Evaluator
  получают объект через конструктор; в тестах им можно передать mock без
  изменения логики хода. Прежний вызов `complete(messages)` сохранён для
  совместимости и ручной проверки. Для будущего Evaluator доступен
  `complete_structured(...)`.

GameService пока запрашивает оценку как текст и разбирает JSON сам. Переход
Evaluator на строгий контракт оценки относится к AI-04/AI-07, а не к AI-02.

## Ошибки

Все ошибки наследуют `LLMProviderError`:

| Тип | Ситуация |
| --- | --- |
| `LLMAuthenticationError` | HTTP 401 или 403 |
| `LLMRateLimitError` | HTTP 429, лимит или квота |
| `LLMTimeoutError` | Истёк таймаут запроса |
| `LLMTransportError` | Нет соединения с API |
| `LLMHTTPError` | Другой HTTP-ответ с ошибкой; содержит `status_code` |
| `LLMResponseError` | Пустой, повреждённый или не прошедший схему ответ |

Сообщения ошибок не содержат ключ API или полный текст ответа модели. Политика
повторов и безопасного восстановления игрового хода относится к AI-11.

## Проверка

`backend/tests/test_llm_provider.py` проверяет обе реализации, JSON Schema,
потоковые фрагменты, валидацию и типы ошибок через `httpx.MockTransport`, без
внешних запросов и расхода гранта.

## MVP-09: выбранный API и ограничения

Для MVP используется Cloud.ru Foundation Models с
`AI_BASE_URL=https://foundation-models.api.cloud.ru/v1` и моделью
`ai-sage/GigaChat3.5-432B-A28B`. В `.env.example` указаны URL и ID модели,
ключ остаётся пустым; реальный ключ хранится только в локальном `.env`.
Провайдер остаётся сменным через `AI_PROVIDER=mock|compatible`.

Согласно [спецификации Cloud.ru](https://cloud.ru/docs/foundation-models/ug/topics/api-ref__specs),
API использует Bearer-ключ, предоставляет `/v1/models` и
`/v1/chat/completions`, принимает `response_format` и `stream`. В
[каталоге моделей Cloud.ru](https://cloud.ru/docs/foundation-models/ug/topics/overview__available__models)
для выбранной модели указаны Structure Output и максимальный контекст
**262 144 токенов**. Это предел модели, а не гарантированный бюджет для
истории: текущий сборщик AI-05 ограничивает недавний диалог 12 сообщениями и
12 000 символами, но пока не считает точные токены всего запроса.

Реальные проверки выбранной модели подтвердили авторизацию, русский текст,
структурированный JSON и потоковый ответ. Отдельный потоковый smoke-тест
25 сентября 2026 года получил 3 текстовых фрагмента за 1547 мс. Время одного
запроса не является гарантией задержки. В игровом ходе пока используется
полный ответ; потоковый метод готов для будущей доставки фрагментов в UI.

HTTP 401/403, 429, таймаут, сетевой сбой, иной неуспешный HTTP-ответ и
повреждённый ответ преобразуются в отдельные типы ошибок провайдера. Ответы
ошибок не содержат ключ или полный текст модели. Проверку предельного
контекста большим платным запросом не проводили.

## Русский smoke-тест AI-03

`backend/tests/test_llm_smoke.py` запускается только при `RUN_LLM_SMOKE=1`.
Для него нужны локальные `AI_PROVIDER=compatible`, `AI_BASE_URL`, `AI_MODEL`
и `AI_API_KEY`. Тест делает два реальных запроса: обычный ответ на русском
и структурированный ответ по Pydantic-схеме. Оба запроса могут расходовать
квоту провайдера.

Пример запуска из корня проекта, если Docker-образ backend уже собран:

```powershell
docker run --rm --env-file .env -e RUN_LLM_SMOKE=1 `
  --mount 'type=bind,source=D:\PATH\TO\PROJECT\backend,target=/app' `
  -w /app negotiation-arena-backend pytest -q -s tests/test_llm_smoke.py
```

Замените `D:\PATH\TO\PROJECT` реальным путём. Без `RUN_LLM_SMOKE=1` обычный
`pytest` пропускает этот тест. Успешный запуск подтверждает, что ключ принят,
получен русский ответ и валидный JSON. В выводе есть только время двух
запросов в миллисекундах; ключ, prompt и ответы не печатаются.

`backend/tests/test_llm_stream_smoke.py` запускается отдельно при
`RUN_LLM_STREAM_SMOKE=1` и делает **один** реальный запрос. Он проверяет
русский потоковый ответ и печатает только число фрагментов и время. Пример
из корня проекта:

```powershell
docker run --rm --env-file .env -e RUN_LLM_STREAM_SMOKE=1 `
  --mount 'type=bind,source=D:\PATH\TO\PROJECT\backend,target=/app' `
  -w /app negotiation-arena-backend pytest -q -s tests/test_llm_stream_smoke.py
```

## Рабочий контракт AI-04

`backend/app/game/evaluator_contract.py` содержит версию `ai04-v1` Pydantic-схемы
по текущему `docs/scoring_and_game_state.md`. Она разделяет наблюдение с цитатами,
PAEI fit, предлагаемый класс события и объяснение. Метод
`validate_evidence(player_message)` проверяет цитаты после валидации JSON.
Примеры и открытые решения перечислены в `docs/api_contracts.md`.
Действующий Evaluator пока использует прежний формат ответа. Подключение новой
схемы к игре требует согласования METH-08/METH-10 и эталонных случаев;
Game Engine должен рассчитывать изменения состояния и итоговый счёт.

## Черновик эталонных реплик MVP-05

`content/evaluator_reference_cases.json` — версионируемый тестовый набор.
Его статус `pending_poliy01`: приведённые оценки являются техническими
гипотезами по черновику `docs/scoring_and_game_state.md`, а не утверждённой
эталонной разметкой. Они не используются в игровом prompt и не меняют
действующий Evaluator.

В файле общий `scenario` задаёт факты и ограничения изолированного тестового
контекста. Каждый элемент `cases` хранит вход отдельно от ожидаемого результата:

- `input.player_message`, `npc_profile`, `phase` и при необходимости
  `state_before` задают ситуацию; иначе используется
  `scenario.default_state_before`;
- `expected.required` задаёт обязательные коды наблюдений и критических
  нарушений;
- `expected.allowed` задаёт допустимые классы действия и диапазон `profile_fit`
  для P/A/E/I. Первый класс — основной черновой вариант, остальные разрешают
  пограничную оценку до методического решения;
- `expected.state_delta_by_action` задаёт ожидаемое изменение `contact`,
  `resistance`, `progress`, `quality` и `critical_errors` для каждого
  допустимого класса. Это результат будущего Game Engine, а не поле Evaluator;
- `review_note` фиксирует спорное место, которое нужно решить при проверке.

`backend/tests/test_evaluator_reference_cases.py` читает JSON как fixture,
проверяет покрытие, совместимость с `ai04-v1` Pydantic-контрактом и соответствие
дельт таблице скоринга. Функция `matches_reference(case, evaluation)` сравнивает
структурированный ответ Evaluator с обязательными и допустимыми значениями,
включая проверку, что цитаты наблюдений встречаются во входной реплике.
Она предназначена для проверки AI-04 после подключения нового контракта.
Тест набора не измеряет точность модели: эталонные оценки и допустимые
альтернативы должен подтвердить или исправить методолог.

Проверка из каталога `backend`:

```sh
python -m unittest discover -s tests -p test_evaluator_reference_cases.py
```

## Сборщик контекста AI-05

`backend/app/game/context_builder.py` собирает приватный контекст из сохранённого
снимка сессии: миссии (текущий аналог уровня), персонажа, PAEI-профиля,
сложности, правил, состояния, памяти и недавнего диалога. Он не делает запросов
к LLM и не читает изменяемые справочники во время хода. `GameService` передаёт
контекст Evaluator, а AI Opponent получает его с уже обновлённым состоянием.

`interests` берутся только из явно сохранённых `mission.context.npc_interests`,
`mission.context.interests` и `character.behavior.interests` в указанном
порядке. Повторы удаляются. Если поля отсутствуют, список пуст: сборщик не
выводит скрытые интересы из произвольного текста. Окончательное имя поля для
интересов в модели данных нужно согласовать в DATA-02.

Приватный контекст содержит скрытые сведения миссии и правила персонажа.
`build_frontend_context(...)` создаёт отдельную публичную проекцию по белому
списку: идентификатор/режим/статус/ход сессии, название и задачу миссии,
`mission.context.public_context`, имя и роль персонажа. Скрытый контекст,
интересы, PAEI, правила, память и история туда не копируются. Текущие API
сессии не отдают приватный словарь сборщика во frontend. Запрос истории
`GET /api/v1/sessions/{session_id}/messages` возвращает только публичные поля;
служебные `payload` и `evaluation` остаются в БД и не сериализуются в ответ.

История включает только завершённые сообщения пользователя и персонажа.
По умолчанию остаются максимум 12 последних сообщений и 12 000 символов
суммарно. Сборщик идёт от новых сообщений к старым, поэтому при переполнении
удаляются старые; слишком длинное последнее сообщение сокращается с начала.
Это предсказуемый предел размера истории, пока для выбранной модели не введён
подсчёт токенов. Новая реплика игрока передаётся отдельно и не теряется при
сокращении истории. Весь сохранённый диалог остаётся в БД для аудита.

`backend/tests/test_context_builder.py` проверяет повторяемость сборки,
разделение приватных и публичных полей, сбор интересов и ограничение истории
без реального LLM.
