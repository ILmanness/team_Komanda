# AI-04: контракт результата Evaluator

> Здесь описан контракт оценки свободной реплики. Пошаговые и короткие тренировки используют подготовленные ответы без Evaluator и AI. Текущие HTTP/WebSocket-маршруты перечислены в [связи экранов с API](frontend_api_gaps.md).

**Рабочая версия `ai04-v1`.** За основу взят текущий
`docs/scoring_and_game_state.md` (разделы 10.2, 10.4, 11.3 и 21.7). Если
методика изменится, создаём следующую версию схемы и сохраняем версию вместе
с результатом для воспроизведения старых ходов. Для свободного текста
используется её расширение `ai10-v1`, описанное ниже. Методические задачи
[`METH-08`](https://github.com/ILmanness/team_Komanda/issues/27) и
[`METH-10`](https://github.com/ILmanness/team_Komanda/issues/28) остаются
открытыми; рабочая версия не означает их формального утверждения.

Модель `backend/app/game/evaluator_contract.py` в версии `ai04-v1` разделяет:

1. `schema_version` — обязательная версия `ai04-v1`;
2. `observations.conversation_progress` — `backward`, `neutral` или `forward`;
3. `observations.features` — признаки с цитатами из реплики игрока;
4. `profile_fit` — четыре обязательные целые оценки P/A/E/I от `-2` до `2`;
5. `proposed_event` — один из шести классов действия и универсальные коды
   критических нарушений из раздела 21.7;
6. `explanation` — короткое объяснение классификации.

Evaluator не возвращает `state_delta`, итоговый счёт или новые значения
`contact`: их должен рассчитывать Game Engine после проверки сценарных правил.
`weighted_paei_fit` считается из `profile_fit` и весов сценария, а не
генерируется моделью. Pydantic проверяет форму ответа, а
`EvaluatorOutput.validate_evidence(player_message)` проверяет, что цитаты
действительно присутствуют в реплике.

## Валидный пример

```json
{
  "schema_version": "ai04-v1",
  "observations": {
    "conversation_progress": "forward",
    "features": [
      {"code": "result_clarity", "evidence": "Нам нужен готовый план к пятнице."}
    ]
  },
  "profile_fit": {"P": 2, "A": 0, "E": 0, "I": 0},
  "proposed_event": {"action_type": "positive", "critical_flags": []},
  "explanation": {"reason": "Названы результат и срок."}
}
```

## Невалидные примеры

- `"profile_fit": {"P": 3, ...}` — значение вне `-2..2`.
- `"action_type": "critical_error", "critical_flags": []` — критическая
  ошибка без кода.
- Критический код при некритическом `action_type` — несогласованная оценка.
- `"conversation_progress": "sideways"` — неизвестное направление.
- `"schema_version": "ai04-v2"` — версия не поддерживается этой схемой.
- Отсутствует `explanation` — обязательное объяснение.
- Добавлено `"state_delta": {"contact": 5}` — Evaluator не меняет состояние.
- Цитата, отсутствующая в реплике, отклоняется `validate_evidence`.

`backend/tests/test_evaluator_contract.py` проверяет эти случаи без LLM.
Для выполнения критерия AI-04 «валидирует все эталонные случаи» нужен
утверждённый набор эталонных реплик по совместной задаче
[`MVP-05`](https://github.com/ILmanness/team_Komanda/issues/5);
`content/evaluator_reference_cases.json` подготовлен как черновик и ожидает
методической разметки и утверждения Полины. Технические тесты проверяют, что
для каждого случая можно построить валидный результат `ai04-v1` и сравнить
его с допустимой разметкой; они пока не измеряют точность ответов LLM.
Формат набора описан в `docs/llm_architecture.md`.

## Методические решения перед интеграцией

- Подтвердить или изменить рабочие шесть классов `action_type`, семь кодов
  критических ошибок и диапазон `profile_fit`.
- Утвердить, какие признаки наблюдения обязательны и какие цитаты считаются
  достаточным основанием для критического флага.
- Утвердить временное соответствие `resistance` в черновом scoring и
  `tension` в действующем состоянии Game Engine.
- Утвердить эталонные случаи и итоговую формулу `METH-10`. Для `METH-10` также
  нужна задача `METH-09` об условиях завершения, выполняемая другими
  участниками. После этих решений можно обновить версию контракта при
  необходимости.

## MVP-10: рабочий результат Turn Evaluator

`TurnEvaluation` расширяет `EvaluatorOutput` отдельной версией `ai10-v1`.
Он обязателен для свободной реплики, оцениваемой LLM; старый `ai04-v1`
сохраняется для чтения черновых эталонов. Новые поля:

- `intent` — одно намерение из `greeting`, `question`, `proposal`,
  `negotiation`, `argument`, `clarification`, `agreement`, `refusal`, `unknown`;
- `paei_markers[]` — буква P/A/E/I, точный фрагмент реплики и уверенность
  `0..1`; список может быть пустым, а разные буквы могут сосуществовать;
- `hint_basis[]` — коды уже наблюдённых `observations.features`, которые
  могут послужить основанием для отдельной подсказки.

Evaluator проверяет JSON через Pydantic и дополнительно требует, чтобы
`features[].evidence` и `paei_markers[].fragment` буквально встречались в
реплике игрока. Неизвестные коды `hint_basis` отбрасываются. Он не возвращает
`effects`, `state_delta` или готовую
подсказку. Игровой движок применяет к `proposed_event.action_type` временную
фиксированную таблицу из `docs/scoring_and_game_state.md` §10.1; её
`resistance` отображается на текущее поле `tension`. Учебные варианты ответа
с явной разметкой по-прежнему проходят по прежнему формату.

Это техническая реализация по черновой методике. Утверждение классов,
эталонных оценок и окончательного соответствия состояния остаётся за
`METH-08` и `METH-10`.

### Подсказка после хода

`POST /api/v1/sessions/{session_id}/hint` требует авторизацию и активную
сессию с завершённым ходом `ai10-v1`. Ответ содержит `level` (1–3),
`hint_type` (`direction`, `context`, `communication`, `mistake`, `strategy`),
`text`, `explanation`, `hints_used` и `remaining`. Готовой реплики игрока и
скрытых интересов в ответе нет. Повтор в пределах одного хода, исчерпанный
лимит, незавершённый ход и терминальная сессия дают HTTP 409.

Лимиты из `docs/scoring_and_game_state.md` §12: Easy — 5, Normal — 3,
Hard — 2. Каждый запрос снижает `negotiation_quality` на 3 пункта в состоянии
сессии; использование сохраняется в `hint_history`. Уровень помощи растёт
от 1 до 3 по числу использованных подсказок. Эта градация является рабочей
реализацией до утверждения `METH-07`.

## Публичная история сообщений (AI-05)

`GET /api/v1/sessions/{session_id}/messages` возвращает для каждого сообщения
только `id`, `session_id`, `sequence_number`, `role`, `content`,
`emotion`, `processing_status` и `created_at`. `emotion` содержит только
`neutral`, `warm`, `tense` или `angry`; для старых сообщений используется `neutral`.
Внутренние `payload`, `evaluation`,
`error_code`, имя модели и счётчик токенов сохраняются на backend, но не
передаются клиенту. Приватный контекст сборщика также не является частью
ответа API.
