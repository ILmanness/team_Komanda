# План разработки MVP «Арена переговоров»

## Статус

Черновик для распределения задач и переноса на Kanban.

## Цель

К 30 сентября 2026 года собрать демонстрируемый веб-MVP, в котором пользователь проходит один законченный сюжет: получает вводную, ведёт свободные переговоры с AI-персонажем, видит изменение игрового состояния, определяет ведущую букву PAEI и получает раздельную обратную связь.

## Роли в задачах

- **Методология** — Полина принимает продуктовое и методическое решение.
- **Техника** — разработчик может выполнить задачу самостоятельно после готовности зависимостей.
- **Совместно** — разработчик готовит варианты и формализует правила вместе с Полиной.
- **Ожидание контекста** — реализация не начинается, пока Полина не передаст или не подтвердит содержание.

## Правила зависимостей

1. Задача не берётся в разработку, если не завершены её обязательные зависимости.
2. Для AI-компонента сначала утверждается JSON-контракт, затем пишется интеграция.
3. Для игровой механики сначала утверждаются методические правила, затем Game Engine и интерфейс.
4. Frontend может начинаться на mock-данных после фиксации API-контракта.
5. Сквозной тест начинается только после работы вертикального среза на одном уровне.
6. Новые удобства не расширяют P0, пока не проходит критический путь.

## Что сокращаем первым, если сроки горят

Сохраняем обязательно:

- один законченный сюжет и один полностью рабочий уровень;
- свободный ввод;
- Evaluator, Game Engine и AI Opponent как отдельные компоненты;
- PAEI Detection;
- практика или обычная игра как минимум в одном режиме;
- финальный результат;
- минимальный тестовый запуск администратора;
- сквозной тест и демонстрационный стенд.

Откладываем в таком порядке:

1. streaming ответа;
2. восстановление сессии;
3. красивый прогресс по всей карьерной линии;
4. расширенные пресеты сложности;
5. копирование и drag-and-drop в админке;
6. полноценную систему ролей;
7. полированный Custom Negotiation Builder.

## Definition of Done для задачи

- результат работает в целевом окружении;
- выполнены обязательные зависимости;
- есть проверяемый сценарий или тест;
- обработана основная ошибка пользователя/интеграции;
- изменения не содержат секретов;
- документация обновлена, если изменился контракт или принято решение;
- Pull Request просмотрен другим участником команды.

## Следующий организационный шаг

После подтверждения этого плана задачи переносятся на Kanban и получают: исполнителя, оценку, ветку, срок, зависимости и статус. Одновременно в работе допускается только то количество задач, которое команда может закончить и проверить до начала следующих.
